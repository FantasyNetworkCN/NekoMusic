# 后端热点性能验证

这里的探针用于比较相同负载下的内存、CPU 时间和操作耗时，不进入生产 JAR，也不连接 MySQL、
Redis 或外部音乐服务。所有输入均为固定种子的合成数据。

## 运行

先使用 Java 27 编译后端并运行测试，然后从 `backend/` 执行：

```bash
bash benchmarks/run.sh
```

脚本需要 `java`、`javac`、`jar` 和 Maven。Maven 不在 PATH 时可指定：

```bash
MVN=/path/to/mvn bash benchmarks/run.sh
```

默认内存场景为 30 万个哈希、每个哈希 4 条 posting，可传入不同的哈希数量：

```bash
bash benchmarks/run.sh 1000000
```

对比旧版本时，先在独立目录编译旧版，再让同一个探针读取旧版编译类：

```bash
NEKO_BENCH_CLASSES=/path/to/before/backend/target/classes bash benchmarks/run.sh
```

`NEKO_BENCH_CLASSPATH_FILE` 可指定已有的依赖 classpath 文本，跳过 Maven 依赖解析。
这些变量仅控制离线探针，不属于后端运行时配置。比较时必须使用相同依赖、JDK、堆大小及输入，
先完成两版编译，再交替运行，避免构建、测试或其他压测与测量并行。

## 测量口径

- 每次运行独立启动 JVM；使用 G1、`-Xms256m -Xmx768m`，先预热再采样。
- `retained_bytes` 用 Java instrumentation 遍历索引可达对象，包含哈希结构、键和 posting 数组。
  它不等于进程 RSS、容器内存、原生分配或整机 RAM。
- `wall_median_us` / `wall_p95_us` 是单次操作墙钟耗时，单位微秒。
- `cpu_mean_us` 是调用线程每次操作的平均 CPU 时间，不包含其他线程的 GC、JIT 或原生工作线程。
- `allocated_bytes` 是调用线程每次操作的 Java 堆分配字节数，不统计 JNI 原生分配。
- `stream_recognition_8s` 使用真实 PCM 转换、Gabor/和声特征提取和识曲服务。旧版按原 WebSocket
  行为复制 PCM，新版同步传入有效前缀。索引已就绪，不包含网络、鉴权、数据库和 FFmpeg 解码。
- 匹配语料包含 2000 组固定查询，覆盖乱序、重复、频率容差、时间缩放、偏移和无关哈希。
  以完整匹配结果的 SHA-256 摘要核对两版行为。
- 和声语料覆盖空输入、帧边界及部分帧，摘要由最终量化特征数组生成。

所有运行的匹配语料摘要一致：

```text
d4868f484dd8d953434579886261b18c5ef6e935ab85cb1e604b0a428d20cd4f
```

所有运行的和声特征摘要一致：

```text
e010e9c4bfa04c9ae7d91d5c48d4ca344c8acbe34ccc3ab0177d426398729954
```

对应实现变化：

- 经典与和声索引使用原始 long 键的只读哈希表，减少装箱键；增量仍共享基础表与未改变的数组。
  哈希数量与 posting 数量预先统计，读取状态和创建增量构建器不再遍历整张基础表。
- 匹配命中使用 long 数组；有序查询跳过排序，乱序查询使用稳定排序，保持相同时间命中的原顺序。
  去重不再拼字符串，对齐中位数共用工作区。
- PCM 读取直接生成 short 样本；实时查询同步借用有效前缀；单窗口提取不再复制整个样本数组。
- 和声提取预计算固定窗函数及频率映射，额外共享约 34 KiB 查表，计算表达式与特征版本保持一致。
- 模糊距离上限为 1 时直接检查首个差异及后缀，不为每个候选构造掩码哈希表或 DP 数组。

最终后端测试为 536 项通过。测试覆盖持久化/增量索引、并发提取、原特征摘要、有效 PCM 前缀、
奇数分块读取、超限输入，以及模糊距离的穷举和 UTF-16 边界。

这些结果支持上述局部优化，不能推算为全站、全部曲库或整机资源按同一比例下降。真实收益仍取决于
曲库的哈希分布、posting 长度、查询内容、并发度、JVM 内存回收及 CDN/数据库/FFmpeg 的占比。
评估 Rust/Go 迁移时应继续使用实际录音回归集、生产负载回放、进程/容器内存及总 CPU 测量。

## 2026-11-21 Rust 迁移

后续改动已将经典声纹倒排存储、查询去重、候选聚合及时间对齐迁移到
`native/recognition/src/lib.rs`。默认构建生成 Rust 动态库，Java 使用 FFM 批量调用。
原生索引使用连续 posting 区域和 16 字节目录槽，增量层由 Rust `Arc` 共享基础索引。
Java 保留音频特征提取、和声兜底、业务接口及不可加载原生库时的告警降级实现。

以下基线是**上一节优化完成后的 Java 版**，不是最初未优化版本。机器、JDK 和采样方式相同。
两版各运行三个独立 JVM，交替顺序为 Java/Rust、Rust/Java、Java/Rust。
原始测量值见 [本轮数据](results/rust-migration-2026-11-21.json)。

| 匹配核心指标 | Java 版 | Rust 版 | 降幅 |
| --- | ---: | ---: | ---: |
| 有序查询：耗时中位数 | 155.943 μs | 136.867 μs | 12.2% |
| 有序查询：调用线程 CPU 时间 | 159.073 μs | 144.964 μs | 8.9% |
| 乱序查询：耗时中位数 | 288.860 μs | 105.132 μs | 63.6% |
| 乱序查询：调用线程 CPU 时间 | 305.697 μs | 106.613 μs | 65.1% |
| 有序查询：Java 堆分配/次 | 137,224 字节 | 606 字节 | 99.6% |
| 乱序查询：Java 堆分配/次 | 167,428 字节 | 256 字节 | 99.8% |

Java 堆分配下降不等于总分配下降：Rust 查询仍会分配候选、去重及对齐工作区，以上分配指标未统计
这些原生临时分配。FFM 查询数据也占用短生命周期的原生缓冲区。

30 万哈希、120 万 posting 的索引数据结构本体由 Java 的 20,691,544 字节，变为 Rust 的
17,988,680 字节。Rust 数值包含目录、posting、Index 和 Arc 引用计数，不包含分配器取整、
动态库、FFM 包装对象或 JVM。探针在此时输出 `heap_index_bytes=-1`，表示未遍历原生包装对象的
可达堆图，不能解释成 Java 零内存占用。

### 恢复索引的实际进程内存

单纯在 Java 里建完整 Map 再复制到 Rust 的原型，曾在 RSS 测量中产生反效果。当前持久化恢复路径
会先用固定 64 KiB 缓冲区预读目录计数，再从同一已打开文件直接写入 Rust，避免恢复全量 Java Map。
没有更改缓存文件格式，旧缓存仍可读取。

进程探针在独立 JVM 生成测试文件，然后让被测进程走真实的 `FullIndexDiskCache.load()`，
使用 `-Xms32m -Xmx768m -XX:+UseG1GC`，读取 `/proc/self/status`。文件包含 100 万个哈希、
400 万条 posting。构建输入的进程与被测进程分离，测量包含动态库、JVM 与索引。

```bash
NEKO_BENCH_PROCESS_MEMORY=1 bash benchmarks/run.sh 1000000
```

| 轮次 | Java RSS（KiB） | Rust RSS（KiB） | Java 恢复耗时（ms） | Rust 恢复耗时（ms） |
| --- | ---: | ---: | ---: | ---: |
| 1 | 191,220 | 170,892 | 376.511 | 455.713 |
| 2 | 194,292 | 173,828 | 377.031 | 483.772 |
| 3 | 191,908 | 171,580 | 382.131 | 524.923 |
| 中位数 | 191,908 | 171,580 | 377.031 | 483.772 |

该场景的 RSS 中位数下降 **10.6%**。代价是恢复索引的调用耗时中位数增加约 107 ms（28.3%），
这包含首次加载 FFM/Rust 库及预读目录；索引启动预热完成后的查询不执行该预读。
这也不代表从所有单曲声纹重新构建索引时的内存峰值下降：重建阶段仍有 Java 构建器，
其转交原生索引时的峰值需要另行测量。

### 完整识曲调用的收益边界

| 场景 | Java 版 | Rust 版 |
| --- | ---: | ---: |
| 8 秒 PCM 服务调用耗时中位数 | 40.256 ms | 40.047 ms |
| 8 秒 PCM 调用线程 CPU 时间 | 40.499 ms | 40.290 ms |

完整调用仍包含 Gabor 与和声特征提取，Rust 迁移相对上一轮 Java 优化仅改善约 **0.5%**，
处于本机测量波动范围，不能据此声称完整 HTTP 请求已获得明显加速。匹配核心和索引恢复场景
的收益应与完整调用收益分别评估。

本轮 2000 组查询的结果摘要与两版 Java 基线一致。验证包括 Rust 单元测试、
`cargo clippy --all-targets -- -D warnings`、541 项后端测试、原生默认启用断言、
并发查询、增量共享、流式恢复、损坏输入，以及脱离源码目录的内嵌库加载。
所有客户端 API 与声纹缓存的版本和契约保持兼容。
